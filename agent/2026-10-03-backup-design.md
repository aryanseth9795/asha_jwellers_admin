# Backup export and import with stable identities (design)

Date: 2026-10-03 · Branch: `feat/ui-revamp` · Status: approved in chat ("Yes, go ahead") · Builds on the owner's
`docs/BACKUP_IMPORT_PLAN.md`

## 1. What the owner asked

> "I want an import button as well to import the backup … unique UUIDs for each transaction and each customer, so if
> there is a backup export and import there is no data integrity problem or data inconsistency … if I lost my local
> data, I import from the backup zip file and the exact data should be imported correctly with all the data
> consistency patterns, without losing or overlapping merging or inaccurate data … with images also. First this, then
> we move to an external database."

**Success:**
- **Exact restore:** after phone loss, Replace-and-restore from a v2 backup reproduces every Asha Jewellers record,
  relationship, stored amount, bill number and photo.
- **Idempotent import:** importing the same backup twice changes nothing the second time.
- **All-or-nothing:** a damaged or invalid backup changes nothing.
- **No overwrites:** no record is overwritten or merged silently.

**Scope:**
- **Covered:** the Asha Jewellers ledger in SQLite, with its photos.
- **Not covered:** SSJ data (bhav, categories, products). It lives on the owner's server (`ssj-server`), not on the
  phone, so it is outside the backup.

## 2. Constraints

- No new dependencies and no native rebuild.
  - The file chooser is `File.pickFileAsync` from `expo-file-system` 19, which is already installed (Android
    `ACTION_OPEN_DOCUMENT`).
  - Zip and unzip use `react-native-zip-archive`, which is already installed. Sharing uses `expo-sharing`.
  - UUIDs are generated by SQLite (`randomblob`), so there is no JS crypto dependency.
- Messages use the notify/confirm system. Pop-ups use `BottomSheet`. Text comes from `src/ui`.
- The existing app behaviour is unchanged. The only intentional fix is in §4.4.

## 3. Identity (database migration)

Every ledger table gains two columns:
- `uuid TEXT`: a UUID v4, unique, and never changed after creation.
- `updatedAt TEXT`: an ISO time.

The 7 ledger tables are `users`, `rehan`, `rehan_transactions`, `lenden`, `jama_entries`, `lenden_items` and
`lenden_old_jewellery_items`.

- **Migration:** once per table, inside one transaction:
  1. `ALTER TABLE … ADD COLUMN uuid TEXT` and `ADD COLUMN updatedAt TEXT`.
  2. `UPDATE … SET uuid = <UUID_SQL> WHERE uuid IS NULL`. SQLite evaluates the expression per row, so every row gets a
     different id.
  3. `updatedAt = COALESCE(<the row's own date column>, now)`.
  4. `CREATE UNIQUE INDEX IF NOT EXISTS idx_<table>_uuid ON <table>(uuid)`.
- **`UUID_SQL`:** one shared SQL expression that formats `randomblob` bytes as a lower-case UUID v4
  (`xxxxxxxx-xxxx-4xxx-[89ab]xxx-xxxxxxxxxxxx`).
- **New rows:** every `INSERT` in `entryDatabase.ts`, `lendenItems.ts` and `lendenOldJewelleryItems.ts` sets
  `uuid = <UUID_SQL>` and `updatedAt = now`.
- **Updates:** every UPDATE sets `updatedAt = now`. This includes the balance updates caused by diya/jama and the baki
  recalculation.
- Numeric `id`s stay local implementation details. Backups never use them as references.

### 4.4 Behaviour fix that consistency needs

- **Bug:** `deleteUser` deletes only the `users` row. `PRAGMA foreign_keys` is off, so the customer's rehan and
  len-den rows are left behind with no customer ("Customer not on file").
- **Fix:** `deleteUser` deletes the customer's rehan (with their transactions) and len-den (with their items, old
  jewellery and jama entries) in one transaction, as `deleteRehan` and `deleteLenden` already do. This matches the
  confirm text "Customer and all transactions deleted".
- **Existing orphan rows are kept, not deleted.** The backup carries them as `customerUuid: null` (§5).

## 5. Backup format v2

The zip contains:

```
manifest.json
data/customers.json
data/rehan.json
data/rehan_transactions.json
data/lenden.json
data/lenden_items.json
data/lenden_old_jewellery_items.json
data/jama_entries.json
media/<recordUuid>/<n>-<originalFileName>
```

`manifest.json`:

```json
{ "format": "aj-backup", "version": 2, "createdAt": "<ISO>",
  "files": { "data/customers.json": { "count": 291, "checksum": "<fnv1a-8hex>" }, … },
  "media": { "count": 120, "missing": 2 },
  "warnings": ["2 photos listed on records were not found on the phone and were left out"] }
```

### Rows

Every stored column is kept. Relationships use UUIDs.

| File | Fields |
|---|---|
| customers | uuid, name, address, mobileNumber, nickname, createdAt, updatedAt |
| rehan | uuid, customerUuid (null = customer not on file), productName, amount, status, openDate, closedDate, media (relative paths), updatedAt |
| rehan_transactions | uuid, rehanUuid, type ("diya" \| "jama"), amount, date, updatedAt |
| lenden | uuid, customerUuid (nullable), date, amount, discount, remaining, jama, baki, status, billNo, amountOverridden, media, updatedAt |
| lenden_items | uuid, lendenUuid, position, name, metal, purity, weight, qty, rate, total, updatedAt |
| lenden_old_jewellery_items | uuid, lendenUuid, position, description, metal, purity, weight, value, updatedAt |
| jama_entries | uuid, lendenUuid, amount, date, updatedAt |

### Checksums and snapshot

- **Checksum:** FNV-1a 32-bit over the exact JSON text of each data file. It detects damage, not tampering.
- **Snapshot:**
  - The export reads all 7 tables inside one read transaction, so the snapshot is consistent.
  - A child row whose parent row no longer exists (impossible after §4.4, but checked) is left out. The export counts
    it in `warnings`.
- **Photos:**
  - Each photo is copied to `media/<recordUuid>/<n>-<name>`. The record's `media` lists those relative paths in the
    original order.
  - A photo file missing on the phone is dropped from the list and counted in `media.missing`.

### Where the export goes

- **Export:** builds the zip, then opens the share sheet, as today.
- **Automatic backup:** an emergency backup is written to `documentDirectory/backups/` before any Replace-and-restore.
  The newest 3 are kept.

## 6. Import pipeline

1. **Pick:** `File.pickFileAsync(undefined, "application/zip")`. If the owner cancels, nothing happens.
2. **Stage:**
   - Copy the file to `cacheDirectory/import-<ts>/backup.zip` and unzip it into the same folder.
   - **v2** is detected by `manifest.json`. **v1 (legacy)** is detected by `users.json`, `rehan.json` and
     `lenden.json` with no manifest.
   - Anything else is rejected as "Not an AJ backup".
3. **Validate (pure, nothing written yet).** Any failure stops the import with a clear error, and the database is
   untouched. The checks:
   - format, version, file list, counts and checksums
   - every row's field types and required fields
   - UUID format and uniqueness within each table
   - every `*Uuid` reference resolving to a row in the same backup (`customerUuid` may be null)
   - `type` being "diya" or "jama"
   - every media path existing inside the zip
4. **Plan (pure):** compare the backup with the local ledger by UUID and show a preview:
   - backup date
   - counts per table
   - new / already here (identical) / conflicting per table
   - bill numbers that clash with a different bill on the phone
   - missing photos
   - for legacy backups, a warning
5. **Choose the mode** in the preview sheet:
   - **Safe merge** (default; not offered for legacy backups)
   - **Replace and restore** (red, with confirmation)
   - **Cancel**
6. **Apply:**
   - **Photos:** copy the backup's photos into the app's images folder as `<recordUuid>-<n>-<name>`. An existing file
     with that name is reused, so re-imports are idempotent.
   - **Database:** write everything in one `withExclusiveTransactionAsync`.
   - **On failure:** the transaction rolls back and the photos this import newly copied are deleted.
7. **Finish:**
   - A success banner shows the summary (added / skipped / conflicts).
   - The staging folder is deleted.
   - Screens reload their data when they regain focus. They already do this.

### 6.1 Safe merge rules (by UUID; a local record is never modified except as stated)

| Record | Absent on the phone | Present and identical | Present and different |
|---|---|---|---|
| Customer | insert | skip | conflict, keep local |
| Rehan (with its transactions) | insert the rehan and all its transactions; `amount` stays as in the backup | skip the rehan | conflict, keep the local rehan |
| Rehan transaction for a rehan present on the phone | insert, and apply it to the local balance (diya +, jama −), as `createRehanTransaction` does | skip | conflict, keep local |
| Len-den (with its items, old jewellery and jama) | insert all of it, stored values as in the backup | skip | conflict, keep the local bill (items are part of the bill and are never merged into it) |
| Jama entry for a len-den present on the phone | insert, then recalculate that bill's jama and baki (`updateLendenBaki`) | skip | conflict, keep local |

- **What "identical" compares:** every exported field except `updatedAt`, and, for rehan, except the derived `amount`
  balance. Rehan transactions are compared one by one.
- **Customer links:**
  - A new rehan or len-den whose customer is a conflict or already present links to the local customer with that UUID.
  - `customerUuid: null` is inserted with `userId = 0` (customer not on file), exactly as in the backup.
- **Bill-number clashes** are reported in the preview and kept as they are. The owner sees them in Data quality.

### 6.2 Replace and restore (the exact restore)

1. Write an emergency v2 backup of the current ledger to `backups/`. If that fails, stop.
2. In one exclusive transaction:
   - delete all rows of the 7 tables
   - insert every backup row with its stored values, uuid and updatedAt unchanged, re-linking children to their new
     local ids through the UUID maps
3. Recalculate nothing. Stored amounts, jama, baki and balances stay exactly as exported. A Jest round-trip test
   proves snapshot → backup → restore rows → the same snapshot.
4. Old photo files are left on disk. They are still referenced by the emergency backup.

### 6.3 Legacy (v1) backups

- They contain only customers, rehan and len-den, with numeric ids, no payments and no items.
- They can be restored with Replace only. The UUIDs are generated during the restore.
- The preview warns: "This is an old backup: jama payments, rehan diya/jama, bill items and old jewellery are not in
  it and cannot be restored."
- Their media paths are `images/<file>`, relative to the old zip.

## 7. User interface

- **Home:** an **Import** button next to **Export**, same style (icon + label).
- **During the work:** a full-screen progress state with "Reading backup…", "Checking…" and "Importing…". The buttons
  are disabled meanwhile.
- **Preview:** a `BottomSheet` titled "Import backup":
  - the date, plus "v2" or "Old backup"
  - a table of the counts (new / same / conflicts for merge)
  - warnings
  - Safe merge and Replace & restore buttons
- **Replace confirmation:** `confirm({ tone: "danger", title: "Replace all data?", confirmLabel: "Replace" })`, with a
  message saying an automatic backup is saved first.
- **Errors:** `notify.error` with a specific reason: "Not an AJ backup", "Backup is damaged (checksum)", "Missing
  photos …", "Unsupported version".

## 8. Units

All units are pure and Jest-tested unless marked otherwise.

| File | Responsibility |
|---|---|
| `src/backup/format.ts` | v2 types, `FORMAT`, `VERSION`, file names, UUID regex |
| `src/backup/checksum.ts` | `fnv1a(text)` |
| `src/backup/serialize.ts` | local rows (numeric ids) → v2 files + manifest; orphan handling; media path mapping |
| `src/backup/validate.ts` | parsed files → `{ ok, errors, data }` |
| `src/backup/plan.ts` | backup data + local snapshot → merge plan and preview counts; replace plan |
| `src/backup/legacy.ts` | v1 JSON → v2 data, with an injected uuid generator |
| `src/database/backupQueries.ts` (device) | snapshot read, migration helpers, `applyMerge`, `applyReplace` in one exclusive transaction |
| `src/services/BackupExportService.ts` (device) | staging, photo copy, zip, share, emergency backups |
| `src/services/BackupImportService.ts` (device) | pick, stage, unzip, read, validate, plan, apply, cleanup |
| `src/components/ImportBackupSheet.tsx` | preview and mode choice |

`ExportService.ts` is replaced by `BackupExportService.ts`. Home calls the new service.

## 9. Testing

- **Jest (pure):**
  - checksum vectors
  - serialize (orphans, media mapping, counts, checksums)
  - validate: every rejection reason
  - plan: insert / skip / conflict for each table, child inserts into existing parents, a re-import being a no-op,
    customer link resolution, bill-number clashes
  - legacy conversion
  - the **round trip**: snapshot → serialize → validate → replace rows equal the snapshot, field for field
- **`npx tsc --noEmit`** clean, and a source-audit rule against `ExportService` imports.
- **Device checklist:**
  - export and then restore into an empty install
  - import the same backup twice
  - a damaged zip
  - two photos with the same name
  - a legacy zip
  - a merge between two phones

## 10. Out of scope

External database and sync, deletion tombstones, encrypting the backup, scheduled automatic backups, and SSJ catalog
data.

## 11. Item category (owner request, 2026-10-03)

- **Description stays free text.** `rehan.productName` and the bill item `lenden_items.name` are unchanged.
- **New optional field `category TEXT`** on `rehan` and `lenden_items`.
- **The value comes from a dropdown:**
  - the 28 item types of the analytics keyword rules (`src/utils/analytics/report/items.ts`, in rule order)
  - "Other"
  - any custom category already stored on a record
  - A new category the admin types is kept as typed (trimmed, first letter capitalised) and reused from then on.
- **Saving:** when nothing is chosen, the record is saved with category "Other".
- **Records saved before this change** have `category` NULL. For those, analytics fall back to the keyword rule on the
  description (today's behaviour). Analytics use `category ?? itemTypeOf(description)`.
- **Backup v2:** `RehanRow` and `LendenItemRow` gain `category: string | null`.
  - Serialize, validate and legacy carry it.
  - The merge planner compares it for rehan. Bill items of an existing bill are matched by uuid only, as in §6.1.
  - The legacy converter reads an optional `category` from refined old files.
- **Refined old backup:** each rehan gets `category` from the same keyword rules, or "Other" when none matches.
